# Arena V2 架构影响与迁移边界

## 文档状态

- 状态：初稿，已完成第一轮原型边界收敛
- 日期：2026-07-27
- 前置原则：继续遵守 Rule → Core → Bot → Presentation

## 总体判断

V2 不需要推翻当前 Arena 的确定性规则、Definition/Registry、Replay、Profile 和产品生命周期基础，但需要把当前“固定本地 1v1”扩展为“可区分模式的战斗运行时”。

先做产品和规则初稿，再做架构重构。不能因为已经确定要增加生存模式，就立即把现有 1v1 代码改成大量条件分支。

## 可以复用的基础

- `InputFrame` 和表现层只读快照；
- 60 Hz 权威 tick 和确定性 seed；
- ActionResolver 和统一命中/击退事件；
- MapDefinition / MapRegistry 的数据定义方式；
- EquipmentDefinition / Registry 的内容注册方式；
- Replay、实验和黄金回放合同；
- Product Session、Profile 和奖励事务的生命周期边界。

## 必须重新设计或扩展的部分

### 1. 模式合同

当前 MatchConfig 以 1v1 参赛者为中心。V2 需要增加显式 `modeId` 和模式规则定义，使生存模式拥有敌人刷新、轮次、掉落、复活和结束条件，而不是伪装成两个玩家的 1v1。

### 2. 战斗单位模型

生存模式的敌人不能全部作为隐藏玩家槽位处理。需要一个能表达玩家、对手和敌人的统一战斗单位边界，同时保留不同的 Bot/Enemy Observation 权限。

### 3. 武器定义

需要区分：

- 不可变的武器基础定义；
- 当前动作和命中效果；
- 武器的地面/空中动作上下文与公开数值投影；
- 生存模式的临时武器等级/Offer；
- 局外收藏和解锁状态。

临时等级不能修改永久 Definition，也不能让表现层直接写入战斗数值。
当前已接入的 `ProductContentPresentationDefinition.overview` 只承担公开展示，不是第二套权威平衡源；最终 V2 迁移时必须把上下文动作和临时等级分别放入 Rule/Core 数据边界。

### 4. 地图定义

现有竞技场地图和跳跃/路线地图应保持不同内容类型。二者可以共享 surface、边缘和危险区基础，但不能用大量模式判断复用同一张地图定义。

### 5. 敌人控制

现有单一对手 Bot Controller 可以继续用于 1v1。生存模式需要独立的敌人生成、观察和行为阶段；敌人数量增加必须是可测量的压力曲线，而不是在 Renderer 中生成模型。

### 6. 产品页面

现有 V1 Screen Registry 需要增加模式选择、武器收藏、武器详情、地图收藏、地图详情和生存准备等内容，但页面状态不能越权修改 MatchCore。

### 7. 成长内容

现有奖励和解锁基础可以复用，但需要支持武器收藏、地图收藏、使用记录和挑战记录。当前空的 UnlockDefinition 内容池不能直接用临时文案填充。

## 推荐迁移顺序

```text
V2 产品总纲
  ↓
模式 / 武器 / 地图 / 成长 Definition 草案
  ↓
无渲染 1v1 武器原型
  ↓
无渲染生存模式最小循环
  ↓
Bot / Enemy Observation 与生成压力
  ↓
页面状态和反馈表现
  ↓
完整资产、平衡和设备验证
```

截至 2026-07-27，推荐顺序中的“无渲染 1v1 武器原型”和“无渲染生存模式最小循环”已经在 `arena-v1-experiment` 形成可复现证据；六段跳跃路线也已接入轻量物理灰盒可达性验证。它们仍属于研究/开发工具链，不是 V2 生产入口。

## 当前不应做的重构

- 不先把所有武器改成最终大系统。
- 不先增加几十把内容来验证收藏目标。
- 不把生存敌人伪装成多个玩家参赛者。
- 不把 1v1 与生存规则写成一个巨大的条件分支。
- 不在研究结论前冻结武器数值、地图数量或 200 小时具体配方。
